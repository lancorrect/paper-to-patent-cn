# 阶段 6：工作流与日志（贯穿全程）

## 版本目录

```
<专利短名>/
├── INDEX.md        本专利的名称、来源论文、当前状态、最新日志
├── logs/           本专利的每日日志
├── paper/          来源论文，不纳入版本体系
├── v1/             首稿。作者手写的基线稿要冻结，任何自动流程都不得覆盖
├── v2/ v3/ …       成稿阶段的迭代
└── revise_v1/ …    代理机构返修阶段
```

### 成稿阶段（vN）

- 作者手写的 `v1` 要**冻结**，后续版本从它派生，但不改它。没有手写稿时，`v1` 就是首份生成稿。
- 每版目录内放该版的全部产物：草案、`论文映射.md`、`figures/`、`word/`、`scripts/`、`snapshots/`。
- **映射表跟随版本**，固定命名 `v<N>/论文映射.md`，不放 `paper/`、不只留在对话里。
- 什么时候新建下一版：距上次版本操作超过 24 小时可以新建；24 小时内除非用户明确要求，改动就落在当前版内。改动量大时主动问用户要不要新建，不自行决定。

### 修改阶段（revise_vN）

- **N 是代理机构返回意见的轮次，不是自己改稿的次数。** 只有拿到新一轮意见才新建目录；自己在本轮意见上改多少次都落在当前目录内。
- 每轮两个文件，角色固定：

  | 文件 | 角色 | 能不能改 |
  |---|---|---|
  | `…修改意见.docx`（或审核稿） | 代理机构返回的原件，带全部批注与修订 | **只读基准，任何情况下不得改动** |
  | `…修改稿_v1.docx` | 本轮实际要改的工作文件，最初是原件的逐字节副本 | 改动全落这里 |

- 新建时不覆盖上一轮，保留完整返修链条。

### 两个阶段的关系

成稿和修改是**先后两个阶段，不是两份互相竞争的事实源**。修改阶段开始后，成稿阶段的最后一版就此冻结作为存档，不存在「哪份为准」「要不要回灌」的问题。

## 工作日志

日志和索引按专利分开，放在各专利目录内，避免多个专利混在一起。一天的工作涉及两篇专利时，各记各的。

- **会话日志**：每天一个 `<专利>/logs/YYYY-MM-DD.md`。更新前先判断今天与本专利最新日志是否同一天：
  - 同一天：直接续写；
  - 新的一天：**先把最新日志复制为新日期文件，再在新文件上改**，未完成任务全量结转。**不得修改历史日志。**
- **索引**：`<专利>/INDEX.md` 记本专利的名称、来源论文、当前状态、最新日志链接。
- **每篇日志至少覆盖**：本次目标、关联专利与来源、论文映射摘要 + 链接（详表在版本目录里，日志不抄整表）、关键决策（含名称演变）、本次文件级变更、附图图号一致性、待解决与风险、下一步。
- 长节不重复誊抄：已经写进 skill 或项目指令文件的通用经验，日志里引用即可，不再复制。
- **节奏**：持续对话中定期提醒用户要不要存日志；形成阶段性结果时直接写，并在回复中告知。

日志的价值在返修阶段体现得最明显：专利文档是二进制，git diff 不可读，**日志才是唯一可读的变更记录**。

## Git

- **提交前必须经用户审核。** 撰写或修改专利文档后不得擅自提交，先把改动（diff 或前后对照）交用户看，明确确认后才提交。
- 文档与日志**一起提交**，避免脱节。
- 不擅自执行破坏性操作（`reset --hard`、`clean -fd`、改写历史）。
- 应当忽略的：系统文件（`.DS_Store`、`Thumbs.db`）、Word 锁文件（`~$*`）、drawio 自动备份（`.$*.bkp`）、一次性的改前备份、压缩包。

## 从论文到递交的完整节奏

| 阶段 | 出口标志 |
|---|---|
| 1 论文分析与骨架映射 | 映射表 + 权项结构经用户审核 |
| 2 撰写 | md 草案五件齐全，自查表全过 |
| 文风校订 | 校验脚本全过 + 用户逐条过目 |
| 3 附图 | 图定稿、导出、图文一致性核完 |
| 4 打包 | verify 全过 + 独立终审 + 用户 Word 目视验收 |
| 5 转正 | docx 成为事实源，快照入库 |
| 交付 | 五件交代理机构 |
| 返修 | 逐条批注销项，修订模式回改，双向验收 |

每个阶段的出口没达成就不要进下一阶段。跳步的代价在后面成倍偿还。
