# 阶段 1：论文分析与骨架映射

这是整条链路最关键的一步。这一步的产出决定后面所有文字的走向，返工成本也最高——权利要求结构定错了，说明书全篇都要重写。

## 核心原则：以专利结构为模具，不以论文结构为起点

新手最容易犯的错，是打开论文从 Introduction 顺着往下读，读到哪写到哪，最后写出一份「论文的换皮版」。这样写出来的稿子有三个必然问题：结构不合规、保护范围偏窄、大量专利用不到的内容占篇幅。

正确做法是反过来：

1. 先把专利必备的每一格铺开（见下表）；
2. 再逐格问「这一格的内容从论文哪里来」；
3. 论文里对不上任何一格的内容，明确剔除。

**论文是素材库，专利结构是模具。** 不让论文章节牵着走。

## 专利骨架表

| 专利部分 | 撰写要求 |
|---|---|
| 发明名称 | 反映技术主题 + 类别；不锁死单一实验或参数；**不超过 25 字** |
| 摘要 | 不超过 300 字：领域 + 要解决的问题 + 核心方案 + 效果 |
| 权利要求书 | 1 条独立权利要求 + 6 到 12 条从属；方法专利的独权须记载 S1–Sn 可执行步骤；从属逐级收窄参数、步骤、方程、数据源、模型模块 |
| 技术领域 | 一段话界定工程或算法领域 |
| 背景技术 | 客观陈述现有技术与其局限，不夸大新颖性 |
| 要解决的技术问题 | 客观技术问题，不是商业目标 |
| 技术方案 | 映射并支撑每一条权利要求，步骤化 S1–Sn |
| 有益效果 | 特征 → 机理 → 效果；区分实测与理论预期 |
| 附图说明 | 逐图说明，与正文图号一致 |
| 具体实施方式 | 可实现的实施例、变体、参数范围、完整数据流 |
| 摘要附图 | 方法专利默认是 S1–Sn 流程图，且必须是说明书附图之一 |

## 产出物：映射表

落到 `<专利目录>/v<N>/论文映射.md`，固定四列：

| 专利部分 | 论文来源（节 / 段 / 式） | 转化处理 | 差异化理由 |
|---|---|---|---|

两条要求：

- **来源要具体到节号、段落、公式编号**。写「见方法节」等于没写，后面核对时还得重找。
- **每一行都要填「转化处理」**。照抄不算转化；专利语言和论文语言不是一回事（见 `02-撰写规范.md`）。

## 默认剔除清单

论文里这些内容专利用不到，在映射表末尾单列一节说明剔除了什么、为什么：

| 剔除项 | 原因 |
|---|---|
| Related Work 整节 | 专利没有这个结构。现有技术的局限并入背景技术，且要改写成客观陈述 |
| Contributions 贡献清单 | 专利不用「我们的贡献是…」这种表述 |
| 数据集「公开发布」这一学术贡献 | 发布数据集不是可专利的技术特征。数据**来源**可以作为 S1 数据获取步骤的一部分提及，「我们发布了它」这层不写 |
| Experiments 的 SOTA 对比与消融 | 最多作为有益效果的佐证。没有真实数据就不写，**绝不杜撰** |
| 致谢、参考文献、作者信息 | 与专利无关 |

## 从论文提取什么

| 要提取的 | 用在哪 |
|---|---|
| 各模块的公式与张量维度 | 技术方案 S1–Sn、具体实施方式、从属权利要求 |
| 模块内部结构（层数、激活函数、归一化） | 具体实施方式的可实现细节 |
| 数据来源与预处理方式 | S1 数据获取步骤 |
| 实验设置（窗口长度、预测步数、指标定义） | 实施例参数、实验验证段 |
| 现有方法的局限 | 背景技术（须改写，不照搬原句） |

## 不能从论文推断的（最重要的一节）

**论文为节省篇幅一定会略去实现细节，从论文文字推断出来的写法很可能是错的。**

真实发生过的例子，全部是作者口述后才写对的，照论文写会写错：

- 时间编码不是只加一次，而是**每一次降维后都注入**（论文只写了「加上时间编码」）；
- 残差块内部**含 BatchNorm**，捷径在变维时用 1×1 卷积对齐（论文只写「残差块」）；
- 稀疏路由的粒度是**单级 top-k**，不是被引论文原文的两级（照原文写就错了）；
- 真实代码里路由只选索引不加权、且路由本身无参数（论文的图容易让人以为有）；
- 下采样的真实结构是 BasicBlock/ConvBlock，与论文的文字描述对不上。

这些写错的后果不只是不准确：说明书写了实际做不到的东西，属于公开不充分；权利要求写了实际没做的特征，将来可能得不到说明书支持。

### 必问清单

动笔前逐项问用户，问不到就不写进说明书，或者用更宽的表述带过：

1. 每个模块的**内部结构**：几层、什么算子、有没有归一化、激活函数是哪个；
2. 每个可训练参数的**形状**，以及张量在每步的维度变化；
3. 每步操作的**真实顺序**（论文的公式顺序常与代码不一致）；
4. 超参的**真实取值**（写进实施例，权利要求里用变量名占位）；
5. 损失函数的**真实形式**（比如代码里是绝对值还是平方，与论文写的未必一致）；
6. 有没有论文里没写、但实际做了的预处理或工程技巧。

问的时候一次性列全，不要挤牙膏式地一轮问一个。

## 多版本论文的处理

同一工作常有多个版本（预印本、投稿版、终稿）。做法：

- **方法细节取公式最全的那版**，说理与动机取表述最成熟的那版；
- 映射表里标明每一行出自哪一版；
- **已公开的那版构成对自己申请的现有技术**，背景技术必须实质改写，不照搬原句。

已公开论文是否影响新颖性、有没有宽限期，属于法律判断，**本 skill 不下结论**，由专利代理人认定。

## 从映射表推出权利要求结构

1. 把技术方案拆成 S1–Sn **可执行步骤**。独权只列步骤，**不堆公式、不带附图编号**；
2. 每条从属盯住一个步骤，带该步的拆短公式；
3. 超参一律用变量名占位，具体取值放实施例——写死取值会把保护范围收窄到那个数；
4. 并列权项（装置、系统、存储介质）默认不写，需要时再加；
5. 权利要求不是论文的贡献清单，不要按「创新点一二三」组织。

### 步骤怎么切

一个步骤应当是「一次有明确输入输出的完整操作」。切得太细会让独权冗长，切得太粗会让从属无处着力。经验值：**方法类专利 6 到 8 步**比较顺手。

## 审核门

**映射表 + 剔除清单 + 权利要求结构，三样一起交用户审核，通过后才进入撰写。**

不要跳过这一步直接出稿。这一步返工只改一张表，出稿后返工要重写全篇。
