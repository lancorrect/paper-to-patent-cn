# 阶段 5：事实源、快照，与直接改 docx 的实务

## 事实源转正

首次成稿、用户开始在 Word 里直接手改之后，**事实源就从 md 草案转成 docx 本身**。此后一切修改直接改 docx，不再回头跑生成脚本。

这不是可选风格，是被一次事故逼出来的规矩：管线原本规定「md 是唯一事实源，任何修改都改 md 后重跑脚本」，但用户直接改了 Word，md 没同步。此时重跑脚本会覆盖全部手改，而两份稿子谁是源已经分不清，只能停下来专门定夺归属。

转正后：

- 旧的 `build_docx.py` **不要再跑**。如果它还在目录里，标注清楚是历史存档，最好连同一份「不得运行」的说明一起放。
- 格式体检脚本要剥离对 md 的依赖，改成纯粹的格式检查。

## 快照机制

docx 是二进制，`git diff` 不可读，所以每次改完导出一份 md 快照一并提交，变更靠快照的 diff 阅读。

```bash
python scripts/export_snapshot.py --project <专利>/v<N>
```

硬性要求：

- 快照放独立的 `snapshots/` 目录；
- 首行写死「自动生成的只读快照，事实源是 ../word/xxx.docx，请勿手改」；
- **禁止写入时间戳等每次运行都变的内容**，否则内容没变也产生 diff 噪音。必须实测幂等：连跑两次，文件字节相同；
- 快照是只读产物，**任何情况下不得手改快照，也不得从快照回灌 docx**。

## 动 docx 之前：先确认没人开着

**这是硬前提，不是建议。**

实测过「Word 开着时强行写入」的完整后果：

- 脚本**零报错，验收全过**，磁盘上确实是新内容；
- Word 界面**没有任何提示**，打开着的窗口里看不到改动（Word 读进内存后不再盯磁盘）；
- 写入后 `lsof` 反而报「未占用」——因为 `os.replace` 换掉了目录项，Word 抓着的是已被替换的旧 inode，而 `~$` 锁文件仍在；
- 用户此时按一次保存，Word 把内存里那份写回原路径，**脚本的改动被静默覆盖，无警告无痕迹**。

这种失败模式比报错危险得多：光看程序输出会以为一切正常。

**所以检查必须在写入前做**：查目录下有没有 `~$*.docx`，有就请用户先关掉 Word。写入后再查什么都查不出来。

## 段落级事实用 python-docx 核

凡涉及「第几段是什么、段落数增减、段落格式」，一律用 `python-docx` 的 `Document().paragraphs` 核。

不要用自写正则扫 `<w:p>`：正则会把表格内的段落一并抓进来，行号与真实段落索引对不上，据此比对会得出错误结论。真实教训：曾据此误判「用户删了标题后的空行」，向用户提了个假问题，还把错误需求写进了任务书。

只有需要粗看全文文字时，才用 `zipfile` 直接读 `word/document.xml`。

## Word 保存会归一化整个 document.xml

Word 每次保存都会重排 XML：合并相邻 run、删除 `w:proofErr`、给 run 加 `w:rsidR`。两个后果：

1. **用户手改过的文件不能与脚本产物做字节比对**，只能做段落级或结构级比对（段落文本、修订计数与作者、批注锚点数量）。
2. **字符串级手术的锚点会漂移。** 用户在 Word 里开关一次文件，原先命中的那段 run XML 可能就不存在了。

   真实案例：某句原本与前文在同一个 run 里，用户撤销手改并保存后被拆成了独立 run，旧锚点直接失效。

   所以脚本必须在替换前**断言「锚点命中次数 == 1」，命中 0 次就中止并重新定位**，绝不允许改成模糊匹配硬凑。那次正是这条断言挡住了误改。

## 在带批注的文件里以修订模式改稿

代理机构通常要求**在原先带批注和审阅的文件里改，保留全部批注与修订痕迹，不得另起干净稿**。于是：

- 不得「接受全部修订」后再改；
- 不得把正文导出成 md 改完重新打包（会丢批注与修订）；
- 脚本直接向 `word/document.xml` 写 `<w:ins>` / `<w:del>`，`w:id` 须避开文件中已有的最大值。

### 作者身份决定 Word 怎么显示（最大的坑）

同样是 `w:ins`，作者名不同，Word 给的是两套完全不同的界面：

| `w:author` | Word 的判断 | 显示 |
|---|---|---|
| 等于当前登录账户 | 「这是我自己改的」 | 红色下划线，点击无弹窗，与手打完全一致 |
| 不等于（任何 Word 不认识的名字） | 「这是别人给的**建议**」 | 另配一种颜色，点击弹出「接受还是拒绝建议？」卡片 |

底层机制没有任何区别，都是 `<w:ins w:id w:author w:date>` 包 `<w:r>`。Word 只按作者是不是当前用户切换 UI。

**所以写入前先从用户手改过的文件里反解出真实账户名**（`word/people.xml` 里的 `w15:person`），不要自己取名。取错了会被当成外来建议，用户一看就觉得「脚本没用修订模式」。

同时要在 `word/people.xml` 里补上对应条目，否则 Word 认不出这个作者。

注意 `people.xml` 的内容随修订状态浮动：用户撤销手改并保存后，Word 会把不再被引用的 `w15:person` 条目删掉。**不能拿它当稳定基准。**

### 公式内的修订写法与正文不同

| | 正文 | 公式（OMML）内 |
|---|---|---|
| 插入 | `<w:ins>` 包 `<w:r>` | `<m:r>` 里包 `<w:ins>`，内含 `<m:t>` |
| 删除 | `<w:del>` 包 `<w:r>`，`<w:t>` 变 `<w:delText>` | **仍用 `<m:t>`**，只是外面包 `<w:del>` |
| 额外 | 无 | `m:sSubPr/m:ctrlPr` 里要写一份同样的 ins/del |

**写之前先从对方文件里反解一份现成结构照抄**，比查规范快且不会错。

公式类改动风险最高（OMML 树结构 + 修订标记双重复杂），改完**必须真开 Word 目视确认渲染无降级**，不能只看 XML 校验通过。

需要新公式时，优先**从文内现成公式深拷贝改造**，不要手写 OMML。

### 验收要双向

改完必须验两件事：

1. **接受修订后**，文字正确、旧内容消失；
2. **拒绝修订后**，与改前逐字相同。

另外核：除改动段外其他段落文本未变、批注条数与内容一字未动、新 `w:id` 无重复且避开原最大值。

**验收批注完整性要比内容，不要比字节**：python-docx 保存会重新序列化它解析过的部件，`comments.xml` 的 XML 声明引号可能由 `"` 变 `'`，字节比对会报红，但批注内容逐字未变。

### 换图片能不能留痕

能。见 `03-附图.md` 末节：修订模式下删旧图 + 插新图，Word 照常留痕。只有「脚本替换 media 字节」和 Word 的「更改图片」不留痕。

## 读取批注与修订

```bash
python scripts/read_revisions.py 稿子.docx          # 批注、修订作者分布、people.xml 账户名
python scripts/diff_docx.py 上一轮.docx 这一轮.docx   # 这一轮新增了哪些修订
python scripts/write_tracked_change.py 稿子.docx --anchor "片段" --replace "新文字" --dry-run
```

用法细节见 `scripts/README.md`。

- 批注在 `word/comments.xml`（`w:comment` 的 id/author/date + 文本），锚点在 `document.xml` 的 `w:commentRangeStart/End` 与 `w:commentReference`；
- 修订是 `w:ins` / `w:del`；
- **批注正文里可能嵌 OMML 公式，只收集 `w:t` 会静默丢字，必须同时收 `m:t`。** 真实案例：两条批注里的关键公式记号就是这样丢的，导致一度看不懂批注在问什么。

### 批注编号和段落索引都会漂移

Word 保存时会重编批注 id。实测一天之内重编过两次，其中一条批注的 id 恰好撞上另一条的旧号。段落索引也随内容增删漂移。

**引用批注一律按内容与锚定文字，不按 id 或段号。** 需要定位时当场重新查。
